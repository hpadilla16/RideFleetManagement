Pantalla 3

Bloqueo por PIN y biometría — y la decisión §9-6

Setup al primer login, unlock por inactividad. El PIN es local al dispositivo (no viaja al backend); N intentos fallidos ⇒ cerrar sesión y volver a login. Usuarios con screenLockExempt no ven este gate.

SetupUnlock + error Variante A: modo kioscoVariante B: sin modo kiosco

Anotaciones · PIN / biometría

14 dígitos: velocidad con guantes gana a entropía — el PIN solo protege la sesión local, el token vive en Keystore. Tras el paso 2 se ofrece activar huella (local_auth).
2Teclas de 62 px, tipografía 23 px: operable con guantes y legible a pleno sol. Teclado anclado abajo = zona del pulgar (una mano).
3Contador de intentos visible; al agotarse ⇒ limpiar sesión y volver a login (re-auth con contraseña). Nunca lockout silencioso.
4Huella como tecla del keypad (tinte morado --p-50 / texto --p-700), no como flujo aparte: un toque, cero modales.
5Escape honesto: "olvidé mi PIN" = cerrar sesión, target de 48 px.
6Variante A: barra persistente --p-800 con salida deliberada (mantener 3 s + PIN). Mientras está activo: lock por inactividad suspendido, notificaciones staff silenciadas, navegación fuera del flujo de firma bloqueada.
7Superficie volteada al cliente: branding del TENANT (display-data), jamás "RideOps"/"Ride Fleet" hardcodeado. Idioma del cliente, no el del empleado.
8Variante B: el canvas de firma resetea el timer con cada trazo; sin barra, sin salida con PIN. Más simple, pero el riesgo dibujado es real (cliente lee los términos y se pausa).
Decisión pendiente de Hector — §9-6 Cuando el cliente firma en el teléfono del empleado, el lock por inactividad no debe saltar a mitad de firma.
  • A · Modo kiosco: + a prueba de pausas largas, + bloquea fisgoneo si el cliente navega; − más build (M4 lo lista como "si §9-6 dice que sí").
  • B · Sin modo kiosco: + barato, listo en M1; − el lock puede disparar con el teléfono en manos del cliente y pedirle el PIN del EMPLEADO (mala imagen y bloqueo del flujo).
Recomendación de diseño: Variante A; si se pospone a M4, lanzar M1 con B + timeout extendido (p. ej. 5 min) SOLO durante CUSTOMER_SIGN_PENDING.

ShellRoute con bottom nav y ubicación activa en el header (header x-view-location en cada request). La nav se esconde por moduleAccess, pero el 403 del backend se maneja igual (DoD-4). El 403 del selector (sin code) se muestra SIEMPRE como negativa visible, nunca pantalla vacía.

Anotaciones · Shell + ubicación

1Ubicación SIEMPRE visible en el header (chip morado --p-50, 44 px + hit-slop a 48). Es el estado que decide qué ve el usuario — no se esconde en un menú.
2Empty por cola, no por pantalla: cada cola vacía lo declara inline (borde punteado, --n-25). La pantalla nunca queda en blanco.
3AGENT = 4 tabs (Inicio, Buscar, Bandeja, Perfil). La Bandeja (outbox, ADR-7) SIEMPRE visible con badge — dead-letter jamás oculto. Checkout e inspección se entra desde las cards, no desde tabs.
4Offline honesto: banner warn con edad del dato ("hace 4 min") + reintento. Los datos cacheados se muestran, no se borran.
5ADMIN/OPS suman Incidentes (issueEscalations) por moduleAccess.issueCenter. La nav se deriva de moduleAccess + role, pero cada request maneja su 403 igualmente (DoD-4). Máximo 5 tabs.
6El sheet solo lista ubicaciones del set del usuario (locationIds; null = todas). Persiste en sesión y alimenta x-view-location y cada fila nueva del outbox.
7403 sin code = negativa de ubicación (REGROUND §1): chrome completo (appbar + tabs), copy claro y 2 salidas (cambiar / reintentar). Prohibido mostrarlo como "no hay datos". Si backend agrega code VIEW_LOCATION_DENIED (gap #3), el mapeo se endurece.
8Skeleton solo en el primer load; los refrescos por polling son silenciosos y el pull-to-refresh muestra su propio indicador. Nada de spinner a pantalla completa.
