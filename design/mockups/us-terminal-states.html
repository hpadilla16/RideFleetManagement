Terminal state vocabulary & fallback paths

A terminal-driven checkout fails in ways a web form never does. The renter walks away mid-signature. The QD2 drops off Wi-Fi. The gateway rejects a payload the terminal never saw. In every one of those, the agent needs one answer to one question: do I wait, retry, or fall back?

Design only — no application code touched. States are named for the responses RFM's existing SPIn client already receives (backend/src/modules/payment-gateway/spin-client.js): GeneralResponse.StatusCode, the fuzzy-approval rule at L172-193, the TERMINAL_NOT_CONFIGURED 409 from spin-charge.service.js, and the 120 s proxyTimeout / 130 s client timeout pair. Every state below resolves to exactly one verdict and at most two buttons. An agent at a counter with a queue does not read paragraphs.

1 · The eleven states — what the agent sees, and what it means

Each card is the banner that replaces the step's action area. The coloured LED and the verdict pill are the whole message; the small print is for the agent who wants it. Spanish shipped alongside on every renter-facing string.

Fall back
The one state RFM cannot currently draw: “Busy”. There is no Terminal / Register model anywhere in the schema — a terminal exists only as an (authKey, tpn) pair in the tenant's settings blob, so one terminal per tenant with no per-location or per-register dimension. Two LAX counters sharing a tenant will collide on the same QD2 and RFM has no way to say who holds it. Drawn here because the failure is real; NOTES §6 phases the fix.
2 · Failure & fallback matrix — the contract this design commits to

Read as: in this state, at this step, money is in this condition, so the agent does this. The Money column is the one that decides whether a failure is an inconvenience or an incident.

State Verdict Money condition Primary action Fallback Notes / code anchor
Step 2 · contract on the terminal
Timed out Retry Nothing charged. Resend the clause that timed out. Accepted clauses are kept. Mint /sign/:token and hand the renter their phone. Both paths stamp tcCompletedAt — the session never forks.
Declined by renter Stop Nothing charged. Return to step 1 and change what they objected to. None. A declined clause is a conversation, not a retry. Coverage decline has its own supported path — declinedInsurance injects a 7th clause.
Terminal offline Fall back Nothing charged. Recheck once — Wi-Fi blips resolve in seconds. Full web fallback: QR signing and HPP payment link for steps 3–4. Falling back for the contract but not for payment strands the checkout half-done.
Gateway rejected Fall back Nothing charged. Nothing in the Dejavoo portal. Do not retry the identical payload. Web fallback, and raise a PaymentOpsFlag so this is investigated. The 2026-05-30 StatusCode 2201 lesson: extra fields are rejected before the terminal is reached.
Step 3 · sale + tokenization
Card declined Retry Nothing captured. Ask for another card — a fresh tap, not a retry of the same one. ManualSaleModal (cash / check / external auth), or an emailed HPP link. The existing manual-override modals stay; they are the counter's real failsafe.
Sale OK, token missing Retry Sale captured. No card on file. Run /v2/Payment/GetCard to tokenize without re-charging. Continue with a persistent warning — never a toast. Silently removes every post-rental autocharge: tolls, fuel, fines, damage. Raise CARD_ON_FILE_FAILED.
Timed out Stop UNKNOWN. The tap may have captured. Query /v2/Payment/Status on the reference before doing anything else. Only after the status query answers. The single most dangerous cell in this table. Never offer “retry” on an unresolved sale timeout — that is how a renter gets charged twice.
Step 4 · security deposit
Hold declined Stop Sale is voided automatically. Explain, then restart payment with another card. ManualDepositModal, or a manager waiver. Existing rollback: sale + failed hold → /v2/Payment/Void, returns rollbackPerformed: true.
Hold declined and void fails Stop INCIDENT — renter charged, no deposit. Do not close the checkout. Escalate. None. This is a human problem now. Raise ROLLBACK_FAILED in the payment-ops queue with the reference and the amount.
Insufficient funds (debit) Retry Sale captured, hold not placed. Offer a credit card — the debit uplift is why the amount rose. Manager waiver, recorded with a reason. applyDebitDepositUplift() raised the amount after the card type was read. Show the renter before the hold, never after.
Any step
Not configured Stop Nothing attempted. Send an admin to Settings → Payment Gateway → SPIn Terminal. None — and that is deliberate. Fail-closed. A half-configured tenant must never be paired with the platform terminal.
Busy Wait Nothing attempted. Wait, or abort the other transaction if it is stale. Web fallback if the other counter is mid-checkout. Needs a terminal-lease concept RFM does not have yet — NOTES §6, phase 3.
The rule the matrix encodes. A failure whose money condition is known gets a button. A failure whose money condition is unknown gets a status query first and no button at all. RFM already learned this the expensive way on the HPP rail — “never trust the redirect”, record only after a server-side queryPaymentStatus. The terminal rail deserves the same posture, and a sale timeout is exactly where it is tested.
3 · The fallback path is the existing product, not a new one

Nothing below is built for this feature. Web signing and the HPP payment link are shipped, live surfaces; the US flow's degradation is simply “become the flow every other tenant already uses”. That is what makes the fallback trustworthy under pressure.

Cost of the fallback
No token, no L3HPP mints with requestCardToken: false and carries no L3 block. A fallback payment therefore loses card-on-file and the interchange benefit. Say so on screen — the agent is choosing, not just clicking.

Hard stop
Waiving needs a manager and a reasonA waived deposit is the tenant deciding to carry the risk. It belongs in the audit log with a name attached, not behind a button any agent can press to make a red banner go away.
One switch, not three. When the terminal is unreachable the agent should press one control — “Switch this checkout to the web flow” — and have the contract, the payment and the deposit all move together. Three independent fallbacks is how a checkout ends up signed on the terminal, paid by link, and holding no deposit at all, with nobody noticing until the car comes back damaged.
